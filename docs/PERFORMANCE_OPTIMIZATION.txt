Dashboard architecture - before and after
-----------------------------------------

* Dashboard layout
    Before : Server Component, calls getMe().
    After  : Unchanged.

* Sidebar
    Before : The whole sidebar was a Client Component. Menus and icons for
             all 3 roles were sent to every user.
    After  : Server Component. Only the current role's menu is sent. Only the
             "active link" logic runs in the browser.

* Admin tables
    Before : Server Components, but the table building block (table.tsx) was
             marked "use client", so every table was hydrated in the browser.
    After  : The table building block is server-only. Tables arrive as plain
             HTML.

* Create / Edit dialogs
    Before : The form, the form library and zod were loaded with the page.
    After  : The form is lazy-loaded when the dialog opens (a skeleton is
             shown while it loads).

* Delete buttons
    Before : sweetalert2 was loaded with every table page.
    After  : sweetalert2 is loaded on the first click (preloaded on hover).

* Search bar
    Before : Debounced 500 ms, but the input lost focus after every search.
    After  : Debounced 500 ms, focus bug fixed, low-priority update, skips
             searches where the text did not change.

3. INITIAL PERFORMANCE BOTTLENECKS AND WHAT HAPPENED TO EACH
-------------------------------------------------------------------------------

The candidates came from reading the code. Each one was then confirmed or
rejected with the bundle analysis and testing.

B1  Large tables rendered fully into the page
    Problem  : No list could handle 1,000+ records; every row would be put
               into the page at once.
    Where    : Students table, AttendanceRoster.tsx
    Result   : CONFIRMED -> FIXED (virtualization on 2 lists, section 6.2)

B2  Heavy client component with broad state
    Problem  : RegistrationWorkspace kept all state in one place, so every
               small change re-rendered the whole workspace.
    Where    : RegistrationWorkspace.tsx
    Result   : CONFIRMED -> FIXED (split into 6 memoized parts, section 6.1)

B3  Large forms bundled with the page
    Problem  : Dialog forms, including zod (381 KB), were downloaded with
               their table pages even when the dialog was never opened.
    Where    : All *Create.tsx dialogs
    Result   : CONFIRMED (biggest problem) -> FIXED for 16 dialogs
               (section 6.4). Full-page forms remain (section 8).

B4  sweetalert2 imported directly in 21 delete buttons
    Problem  : 74 KB loaded on every table page, only needed after Delete.
    Where    : All *Delete.tsx components
    Result   : CONFIRMED -> FIXED (loaded on first click, section 6.4)

B5  Unused / misused dependencies
    Problem  : @tanstack/react-table and dotenv never used; "cn" package
               suspected; two form libraries.
    Where    : package.json
    Result   : PARTLY CONFIRMED
               - FIXED    : removed @tanstack/react-table and dotenv.
               - REJECTED : "cn" is shadcn's own small replacement for
                            clsx + tailwind-merge. Replacing it would save
                            nothing, so it was kept.
               - KEPT     : react-hook-form is only used on login/verify
                            pages, not in the dashboard.

B6  Sidebar re-renders on every navigation and ships as client code
    Where    : DashboardSidebar.tsx
    Result   : CONFIRMED -> FIXED (Server Component + memoized menu items,
               sections 6.1 and 6.5)

B7  Only one debounced input, and the search box loses focus
    Where    : SearchBar.tsx, RegistrationWorkspace.tsx, AttendanceRoster.tsx
    Result   : CONFIRMED -> FIXED / IMPROVED (4 debounced inputs, focus bug
               fixed, section 6.3)

B8  High-frequency events not throttled (scroll, screen-size check)
    Where    : DashboardMainContent.tsx, use-mobile.ts
    Result   : CONFIRMED -> IMPROVED (requestAnimationFrame + useRef for
               scroll, useSyncExternalStore for screen size, section 6.3)

B9  Heavy public-page libraries (three, framer-motion) leaking into the
    dashboard
    Where    : Home page components
    Result   : REJECTED. The analyzer shows they are in NO dashboard page and
               are already lazy-loaded on the home page. No change needed.

N1  NEW FINDING: table.tsx marked "use client" without any interactivity
    Problem  : All 38 tables were hydrated in the browser for no reason.
    Result   : CONFIRMED -> FIXED (section 6.5)

N2  NEW FINDING: search input lost focus after each debounced search
    Problem  : The input was re-created (key={searchTerm}) after every
               search, so the cursor jumped out while typing.
    Result   : CONFIRMED (bug) -> FIXED (section 6.3)

Summary: at least 3 bottlenecks were required. 9 were confirmed
(B1-B4, B6-B8, N1, N2), 1 was partly confirmed (B5), 1 was rejected (B9).

6.2 DOM VIRTUALIZATION & LARGE DATA  (Requirement 3, fixes B1)
---------------------------------------------------------------

Virtualization means only the rows that are visible (plus a small buffer)
exist in the page. When you scroll, rows are reused. A list of 1,000 students
keeps about 20-35 rows in the page instead of 1,000.

(1) Instructor > Attendance roster
    - Virtualized with TanStack Virtual, overscan of 8 rows. Rows are
      measured after they render, so different heights stay aligned.
    - New filter box (name, e-mail, roll number).
    - Files: instructor-dashboard/_components/AttendanceRoster.tsx
             instructor-dashboard/attendance/[sessionId]/page.tsx

(2) Admin > Students > "All (scroll view)" tab
    (new tab; the existing Active / Deleted tabs are unchanged)
    - Loads up to 1,000 students and shows them in a virtualized grid with
      a sticky header and horizontal scrolling on small screens.
    - Edit, Delete and Restore still work on every row.
    - The list code is lazy-loaded, so the normal paginated page does not
      pay for it.
    - Files: admin-dashboard/_components/student/VirtualStudentList.tsx
             admin-dashboard/_components/student/VirtualStudentListLazy.tsx
             admin-dashboard/_components/student/StudentTable.tsx

Representative data (1,000+ records)
    The real database does not yet contain 1,000 records, so both lists
    accept "?demo=1000" (up to 5,000), which adds generated, realistic rows.
    The rows are the same every time, so before/after tests are comparable.
    Saving and row actions are disabled for generated rows, and a notice is
    shown. Without the parameter nothing changes.

      /instructor-dashboard/attendance/<sessionId>?demo=1000
      /admin-dashboard/students?view=all&demo=1000

    File: lib/demo-data.ts

Improvement:
    With 1,000 records the page holds about 20-35 row elements instead of
    1,000+, so scrolling stays smooth and memory use stays flat.


6.3 STATE DECOUPLING & EVENT OPTIMIZATION  (Requirement 4, fixes B7, B8, N2)
----------------------------------------------------------------------------

(1) Debounced server search - kept and improved   [components/ui/SearchBar.tsx]
    - FIXED: the input no longer remounts after each search, so focus and
      cursor stay in place while typing (bug N2).
    - IMPROVED: skips the request when the text did not really change, and
      runs the URL update as a low-priority transition so typing never
      stutters.

(2) Debounced filter (250 ms) - Attendance roster
    Filtering 1,000+ rows waits until the user stops typing.

(3) Debounced filter (250 ms) - Students "All" view
    Same pattern for the virtualized student list.

(4) Debounced filter (250 ms) - Course Registration
    Filter available sections by course code, title or room.

(5) Selective subscriptions (external store) - Attendance roster
    Each student's status lives in a small store outside React. Each row
    subscribes only to its own student (useSyncExternalStore), so changing
    one status re-renders ONE row instead of the roster and all its rows.

(6) External store for screen size - hooks/use-mobile.ts
    Subscribes directly to the browser's media query. It is only notified
    when the mobile breakpoint is crossed, and it avoids an extra render
    when the page loads.

(7) useRef + requestAnimationFrame - components/dashboard/DashboardMainContent.tsx
    The scroll position is kept in a ref (no re-render). Scroll events are
    processed at most once per frame, and React state only changes when the
    new "Back to top" button needs to appear or disappear.

(8) useRef for mutable values - SearchBar.tsx
    The debounce timer and the input element are refs and never trigger
    renders.

Shared helper: hooks/useDebouncedValue.ts

Requirement check: at least 2 debounced interactions and 1 state/update
optimization were required. Delivered: 4 debounced inputs and 4 state
optimizations.

6.5 SERVER / CLIENT COMPONENT BOUNDARIES  (Requirement 6, fixes B6, N1)
-----------------------------------------------------------------------

(1) Dashboard sidebar -> Server Component
    Before : Client code. Every user downloaded the menu definitions and
             icons for all three roles, and the static header and footer
             (logo, user name, e-mail) were hydrated in the browser.
    After  : The server picks the user's role and sends only that role's
             menu, with icons already rendered as HTML. Header and footer
             are plain server HTML. Only the active-link highlight and
             closing the mobile menu run in the browser.
    Files  : components/dashboard/DashboardSidebar.tsx   (server)
             components/dashboard/DashboardSidebarNav.tsx (small client part)

(2) Table building block is no longer client code
    Before : components/ui/table.tsx had "use client", so all 38
             server-rendered tables sent the table code to the browser and
             hydrated every row and cell.
    After  : The directive was removed. Tables are plain HTML; only the
             interactive pieces inside them (Edit, Delete, Restore buttons)
             are client components.

(3) Dialog shell vs. form
    The page table stays a Server Component, the button/dialog shell is a
    tiny Client Component, and the heavy form is a separately loaded Client
    Component.

How this reduces client-side JavaScript:
    Code for static parts is no longer sent to or executed in the browser,
    and fewer components need hydration. The JavaScript shared by every
    dashboard page went from 232 KB to 229 KB (gzip). The bigger benefit is
    less hydration work on table pages, because table rows are no longer
    client components.

8. REMAINING LIMITATIONS / BOTTLENECKS
-------------------------------------------------------------------------------

1. Full-page forms are still heavy (about 354 KB gzip).
   Student Registration, Instructor Registration, Create Department/Program
   and the edit-profile pages need the form immediately because the form IS
   the page, so lazy-loading would not help. A future fix is moving to
   zod/mini or loading only English zod messages, which requires rewriting
   every schema.

2. Framework baseline (about 201 KB gzip on every page).
   Next.js, React and Base UI are shared and cached between pages, but
   cannot be reduced without changing libraries.

3. Fonts.
   The design uses four font families. They are self-hosted and only the
   Latin subset is preloaded; using fewer families would need a design
   decision.

4. "All students" loads up to 1,000 records in one request.
   Larger datasets should use infinite loading (fetch the next page while
   scrolling).

5. The attendance page is 8 KB bigger because of the virtualization library
   (accepted trade-off).

6. Backend response time affects real page speed. Slow API calls show as
   skeletons and are outside the scope of this frontend work.

7. Lighthouse, React Profiler and Core Web Vitals values still need to be
   recorded in a browser with a logged-in user (sections 4 and 7).
